# 04 — Offline-first Windows station: architecture review and risks

Status: review of the **intended** design (`ARCHITECTURE §8, §11–§12, §17`, `API_CONTRACT`, `SECURITY_MODEL`, ADR-0003/0004/0009/0011/0012/0014/0023/0024). Only a stub exists in code: `apps/station-agent` serves `GET /local/v1/status` (`simulator_stub`, `non_operational`, pinned `deployment_id`/`environment_kind`) and nothing else — no engine, journal, SQLite, broker, driver, transport, sync, local auth, installer or update. This review does not connect to instruments, implement calibration, or change any ADR.

**Product requirement taken as given:** CalOS ultimately runs as an offline-first application installed on every Windows calibration workstation. **Design of record:** a Windows-service Station Agent (Python + PyVISA) with a loopback Local API, SQLite (WAL) journal as the source of truth, a sync client with an outbox, and the same React build served locally (ADR-0011, Proposed). Only ADR-0003 (SQLite journal) is Accepted.

## 1. Assessment of the intended architecture

| Aspect | Verdict | Notes |
|---|---|---|
| Journal as source of truth, projections by replay, hash chain, resume policy per node | **Strong** | Matches the evidence goals (AC-ARCH-05, FS-02, FS-09). Needs kill-at-boundary tests on Windows and a defined behaviour for torn writes. |
| Single-writer per run, lease/epoch for cross-station | **Strong** | Provisional-run handling after a rejected lease needs a business process (ST-07). |
| Offline by construction (config pulled, outbox pushed) | **Strong** | Central never talks to instruments (AC-ARCH-04). |
| Local API on loopback with per-session token | **Adequate, under-specified** | Loopback is not an isolation boundary on a shared Windows PC (ST-03). |
| Windows service + MSI + signed updates + auto-rollback | **Adequate, incomplete** | Offline distribution, migration rollback and trust-root expiry are not specified (ST-05). |
| Offline operator authentication (cached grant + local credential) | **Weak until Q-07 is decided** | Clock rollback and revocation latency (ST-04). |
| Safety: Hardware Limits store, fail-closed H2+ | **Strong design, delivery channel missing** | Offline pack update/expiry channel (ST-09). |
| Delivery as "desktop application" | **Not decided** | ADR-0011 vs the stated product form (ST-01). |

## 2. Risks and gaps — to address **before** operational station development

Severity: **High** = resolve (decision or spike) before station code that touches runs/instruments; **Medium** = resolve in the station design phase; each row names the evidence that closes it.

| ID | Sev | Risk | Why it matters | Closing action / evidence |
|---|---|---|---|---|
| **ST-01** | High | **Delivery model undecided.** ADR-0011/0012/0014/0009 are *Proposed*; the product is described as a desktop application; Electron/Tauri/WebView2 are not baseline. A wrong early choice reshapes the installer, update, kiosk, token and CSP design. | Everything downstream (ST-03, ST-05, ST-10, ST-14) depends on it. | Decide LA-DP-01 by ADR; spike SP-6. Frontend stays host-neutral meanwhile. |
| **ST-02** | High | **SQLite durability on real Windows benches.** WAL with `synchronous=FULL` is correct on paper; in practice Defender/other AV scanning of `-wal`/`-shm`, backup agents (VSS) copying a live DB, redirected profiles/OneDrive/network paths, USB-attached or consumer SSDs with volatile caches, and abrupt power loss can corrupt or stall. One agent process plus UI readers share the file. | A lost or corrupt journal is lost calibration evidence (FS-02, FS-09, FS-15). | Fix the DB location (`%ProgramData%\CalOS\…`, ACL'd, excluded from sync clients), require local fixed disk; SP-2: power-cut/kill/AV tests on real hardware and VM snapshots; documented AV exclusion guidance; integrity check at start; scheduled local backup to a second location; torn-write and disk-full tests added to the fault-injection suite. |
| **ST-03** | High | **Local API security model.** `127.0.0.1` is reachable by every local user/process (RDP/shared PCs, malware, other browser tabs via DNS rebinding). ADR-0011 specifies a per-session token, `Host`/`Origin` allow-list and CSP but not: how the token reaches the browser (never in a URL that lands in history/logs), per-Windows-user binding, port stability ("random-but-persisted" gives a fixed target), CORS posture, CSRF for state-changing calls, request size/rate limits, SSE auth, token expiry on lock. **F-05 from the PR #11 review (no CSP/headers/enforcement test) belongs here.** | The local UI can trigger run control; a hijacked session is a safety event. | Write the Local API security spec: one-time launch code exchanged for an `HttpOnly; SameSite=Strict` cookie bound to the Windows session/user; per-boot random port; strict `Host`/`Origin`; CSP header (OF-09) + `frame-ancestors 'none'`; no CORS; idempotency keys + CSRF token on mutating calls; limits; SP-3 prototype with a negative-test suite (rebinding, cross-user, cross-origin, token replay). Consider a Windows named pipe/ACL alternative to TCP for non-browser clients. |
| **ST-04** | High | **Offline identity and time.** Offline grants (ADR-0014) assume trustworthy time to enforce TTL; a user can roll the clock back; monotonic time does not survive reboots; revocation cannot propagate offline; PIN brute-force/lockout and recovery are unspecified; Q-06 (max offline duration) and Q-07 (offline auth model) are open. | Unauthorised or expired operators could start/approve work; evidence timestamps could be questioned (FS-14). | Decide Q-06/Q-07; design a trusted-time scheme (last-seen-central watermark + monotonic/boot_id evidence + skew flags; never rewrite event times); lockout policy; signed grant format with `not_after` and station binding; tests for clock rollback and reboot. |
| **ST-05** | High | **Update, migration and rollback while offline.** Updates arrive by signed media (sneakernet) as often as by network; "never update during an active run" must be reconciled with stations that are rarely idle; forward-only DB migration + "refuse newer schema" makes **agent rollback impossible after migration** unless an N/N-1 compatibility window exists or a verified pre-migration backup is restored (losing later events); trust metadata expiry/rotation (ADR-0004, SR-H1–H3 open) can strand an offline fleet. | A failed update on a bench with no connectivity is an outage; a rollback must not lose evidence. | Specify: N/N-1 DB and API compatibility for one release; backup-and-restore only as a last resort with declared loss; maintenance-window policy; offline Release Package import with full verification; trust-root rotation/expiry plan and test (SP-5); health check + automatic rollback tests (FS-19). |
| **ST-06** | Medium | **Time source policy.** Windows time service config, DST/time-zone, VM/hibernation jumps; events carry `wall_utc`/`monotonic_ns`/`boot_id`, but nothing defines what is *acceptable* skew or what the operator sees. | Review of records, FS-14. | Define thresholds, UI states (`HostStatus.clock`, OF-05), and review flags. |
| **ST-07** | Medium | **Sync edge cases (ADR-0009 Proposed).** Provisional runs started offline can be rejected at central (duplicate claim, stale basis) *after* the physical work is done; large evidence uploads on poor links; enterprise TLS-inspecting proxies vs station authentication; ordering across runs; outbox cursor durability across restore; declared loss of unsynced tail after corruption. | Orphaned evidence and silent data loss are the worst failure for a record system. | Business process for rejected provisional runs (quarantine + human resolution, never discard); proxy/TLS guidance; resumable chunked uploads with digest checks; sync conformance and chaos tests (FS-10…12, FS-17). |
| **ST-08** | Medium | **Hardware access from a service.** Services run in Session 0 under a low-privilege account; USBTMC/GPIB/serial driver ACLs, NI-VISA/other VISA runtime licensing and redistribution, driver install needs admin, per-session VISA resource managers, antivirus/USB policies. ADR-0012 leaves "service wrapper vs host" to a Phase 0 spike. | Discovery and control may work in a console demo and fail as a service. | SP-1: service under the intended account with a **simulator/loopback** transport first, then (later, with explicit approval) a real-VISA compatibility check on a test bench; capability report (FS-23); IT prerequisites document. **No real instrument is connected by this review.** |
| **ST-09** | Medium | **Hardware Limits Pack delivery and expiry offline.** The store must be unwritable by any application component (AC-ARCH-09) yet updatable by a signed "safety channel"; pack expiry relies on wall time that can be rolled back. | Fail-closed behaviour (FS-28) must hold on air-gapped stations. | Specify the signed media import path, an elevated installer/maintenance tool as the only writer, expiry using trusted time (ST-04), and tamper/expiry tests. |
| **ST-10** | Medium | **Multi-user and session model.** Fast user switching, RDP, two browsers on one agent, kiosk lock, operator vs Windows identity (A-06: no shared logins), one active run per instrument resource. | Wrong-user attribution; two UIs controlling one run. | Define UI session model (one control session per run, others read-only), lock/timeout behaviour, kiosk hardening owned by IT with a checklist. |
| **ST-11** | Medium | **Offline observability and support.** No Internet means no remote logs; logs rotation, redacted diagnostic bundles (no secrets/PII), health page, error codes users can read out. | MTTR; secrets in logs (`AGENTS §2.10`). | Local diagnostics spec + redaction tests; UI `HostStatus` and a "copy diagnostics" action. |
| **ST-12** | Medium | **Deployment identity (D-25).** The code and Compose already use `production_rehearsal`; ADR-0024 says `{test, production}`. A station pins `{deployment_id, environment_kind}` and must reject others (FS-27). | New signed schemas that embed the value become hard to change. | Resolve D-25 before any signed artefact or station enrolment embeds the vocabulary. |
| **ST-13** | Medium | **Data protection and retention.** At-rest encryption is optional (SQLCipher licensing); BitLocker is an IT assumption; operator PII; immutability vs deletion obligations. | Compliance and customer acceptance. | Decide policy (encryption requirement, retention schedule, pseudonymisation) before storing operator data. |
| **ST-14** | Medium | **Packaging and signing.** Embedded Python size and patch cadence, Authenticode certificate custody, SmartScreen/AV false positives, per-machine MSI, supported Windows/Edge versions, SBOM per build, reproducible builds. | A fleet-wide installer is the largest single supply-chain surface. | SP-4: build the MSI with the stub agent only, sign with a *test* certificate, document support matrix; no production signing key is created. |
| **ST-15** | Medium | **Frontend ↔ agent contract.** `/local/v1` needs an OpenAPI source, problem+json with stable codes, SSE reconnect/replay semantics, idempotency for operator actions, **no optimistic UI for safety-relevant actions**, and N/N-1 compatibility between the UI build and the agent that serves it. | The UI must never show a state the journal has not committed. | Generate `api-client` from OpenAPI (when the API exists); contract tests; UI states for pending/confirmed/failed per action (OF-05, OF-07). |

## 3. Spikes recommended before operational station development (documentation and non-operational prototypes only)

| Spike | Question | Output | Must not |
|---|---|---|---|
| SP-1 | Service hosting + Session 0 + low-privilege account; can the agent run a **simulator** transport and an interactive UI session? | Written findings, prototype service with the stub | Touch a real instrument |
| SP-2 | SQLite WAL/FULL durability on Windows with AV, VSS backup, kill and power-cut (VM + one physical bench PC) | Reproducible test report, location/ACL/AV guidance | Use production data |
| SP-3 | Local API session model (launch code → cookie, per-boot port, Host/Origin/CSP) with negative tests | Security spec + prototype + test suite | Store real credentials |
| SP-4 | MSI build/sign/update/rollback with the stub agent and a **test** certificate | Support matrix, update-failure drills | Create or store a production signing key |
| SP-5 | Offline Release/Update import, N/N-1 migration window, trust-root expiry drill | Compatibility rules, test vectors | Activate any trust root |
| SP-6 | UI delivery: Edge app-mode/kiosk vs a WebView2 thin host (Hebrew IME, shortcuts, print, scaling 125–150 %) | Comparison and recommendation for LA-DP-01 | Add Electron/Tauri without an ADR |

Each spike is a documentation-first branch with a time-boxed prototype and an explicit statement of what it did **not** verify.

## 4. Recommended order for station work (all after the gates above)
1. Decisions: LA-DP-01 (delivery), Q-06/Q-07 (offline duration/auth), D-25 (environment vocabulary), ADR-0009/0012/0014 ratified or revised.
2. Spikes SP-1…SP-6 (docs + stub prototypes).
3. Pure libraries with fake ports and no I/O: journal envelope + hash chain, projections/replay, resume algorithm (`calos_engine`, `calos_audit`) — property and kill-at-boundary tests, **simulator only**.
4. SQLite adapter and migrations at the station with backup/forward-only rules.
5. Local API + local auth + UI session model; frontend `HostStatus` adapter.
6. Sync client against a central stub (idempotency, gaps, quarantine).
7. Installer/update. Only then, and only with the MI register inputs and the approvals in `IMPLEMENTATION_ROADMAP` Phase 4, any real transport.

## 5. Frontend implications (so WP-1A-1e does the right preparatory work)
The frontend should already model: a `HostStatus` port with explicit offline/stale/unknown states (OF-05); host-supplied time (OF-06); hash routing and no service worker (OF-02/03); a CSP-clean build (OF-09); actions disabled-with-reason when the host is unavailable (OF-07); no optimistic updates for host-committed state (ST-15). None of these require the Station Agent to exist; all can be exercised with a fake port.
